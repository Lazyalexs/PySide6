# Архитектура системы обмена файлами в закрытой сети

**Условия:** 7 рабочих станций + 1 сервер, Windows 10, сеть без выхода в интернет, общие сетевые папки запрещены. Файлы — до нескольких гигабайт. Модель работы — почтовый клиент: адресная передача, а не общее хранилище.

Рабочее название системы — **FilePost**.

---

## 1. Общая схема

```
[ПК-1] ─┐
[ПК-2] ─┤
[ПК-3] ─┤   HTTP (порт 8080)      ┌──────────────────────┐
[ПК-4] ─┼───────────────────────► │  СЕРВЕР              │
[ПК-5] ─┤   чанковая загрузка     │  FilePost Service    │
[ПК-6] ─┤   Range-скачивание      │  ├─ FastAPI/Uvicorn  │
[ПК-7] ─┘                         │  ├─ SQLite (WAL)     │
                                  │  └─ Хранилище (NTFS) │
                                  └──────────────────────┘
```

Модель передачи — **store-and-forward**: отправитель заливает файл на сервер, сервер хранит его до тех пор, пока получатель не заберёт. Получатель может быть выключен в момент отправки — это и есть главное отличие от прямой передачи и причина, по которой заказчик просил «как почту».

Плата за это — двойная передача (ПК → сервер → ПК). На гигабитной сети файл в 5 ГБ идёт около минуты в каждую сторону.

---

## 2. Сервер

### 2.1 Компоненты

| Компонент | Назначение |
|---|---|
| **API-слой** | FastAPI + Uvicorn, обработка HTTP-запросов |
| **Auth** | Регистрация станции по коду, ключ станции → токен с TTL, проверка на каждом запросе |
| **Storage Manager** | Приём чанков, сборка, атомарное перемещение, раздача с Range |
| **DB** | SQLite в режиме WAL: станции, сообщения, вложения, аудит |
| **Housekeeper** | Фоновый планировщик: уборка мусора, ночной бэкап БД, опциональная очистка по сроку |
| **Audit Log** | Журнал всех операций: кто, кому, что, когда, скачал ли |

Запуск как служба Windows через **NSSM** — чтобы работало без залогиненного пользователя и поднималось после перезагрузки.

### 2.2 Структура каталогов на сервере

```
D:\FilePost\
├── storage\           постоянное хранилище
│   └── 2026\08\{uuid}.bin
├── tmp\               незавершённые загрузки (тот же том!)
│   └── {upload_id}\chunk_0000, chunk_0001, ...
├── db\
│   └── filepost.db
├── logs\
│   ├── app.log
│   └── audit.log
└── config.toml
```

`tmp\` и `storage\` обязаны лежать **на одном томе** — тогда финальное перемещение собранного файла это мгновенный `rename`, а не повторное копирование гигабайтов.

### 2.3 Схема базы данных

**stations** — станции с установленным клиентом; она же адресат

| Поле | Тип | Комментарий |
|---|---|---|
| id | INTEGER PK | |
| display_name | TEXT UNIQUE | «Бухгалтерия, окно 2» — имя из настроек клиента, единственное, что видят люди |
| machine_name | TEXT | имя ПК из Windows, только для диагностики |
| secret_hash | TEXT | ключ станции, выданный при регистрации (bcrypt/argon2) |
| last_ip | TEXT | только для диагностики, в клиенте не показывается |
| client_version | TEXT | видно, где остался старый `.exe` |
| is_active | INTEGER | вывод станции из эксплуатации = деактивация, не удаление |
| is_admin | INTEGER | админские разделы в клиенте и `/api/admin/*` |
| first_seen_at | TEXT | |
| last_seen_at | TEXT | обновляется на каждом запросе, отсюда статус «в сети» |

**Одна станция — один адресат.** Отдельной сущности «пользователь» в системе нет: клиент установлен на конкретном ПК, у этого клиента есть имя, и письма адресуются именно ему. Список получателей и список машин с клиентом — это один и тот же список, а не два связанных.

`display_name` **задаётся в настройках клиента**, но хранится на сервере и раздаётся остальным. Разделение здесь такое: право менять имя принадлежит станции, а единственная копия — серверу. Держать имя только локально нельзя — тогда на каждой машине был бы свой набор названий и договориться, кто есть кто, стало бы невозможно.

Уникальность обязательна: две «Бухгалтерии» в выпадающем списке — это файл, отправленный не туда. Имя не копируется в сообщения, связь идёт по FK, поэтому после переименования и старая переписка показывает актуальное название.

**tokens**

| Поле | Тип | Комментарий |
|---|---|---|
| token | TEXT PK | |
| station_id | INTEGER FK | |
| expires_at | TEXT | |

**messages** — конверт

| Поле | Тип | Комментарий |
|---|---|---|
| id | INTEGER PK | |
| sender_id | INTEGER FK | станция-отправитель |
| subject | TEXT | |
| body | TEXT | комментарий к передаче |
| status | TEXT | `draft` / `sent` |
| created_at | TEXT | |
| sent_at | TEXT | |
| deleted_by_sender | INTEGER | скрыто в «Отправленных», файл на диске остаётся |

**message_recipients** — по строке на каждого получателя

| Поле | Тип | Комментарий |
|---|---|---|
| id | INTEGER PK | |
| message_id | INTEGER FK | |
| recipient_id | INTEGER FK | станция-получатель |
| is_read | INTEGER | открыл сообщение |
| downloaded_at | TEXT | забрал вложения — аналог уведомления о доставке |
| deleted_by_recipient | INTEGER | скрыто у получателя, файл на диске остаётся |

**attachments**

| Поле | Тип | Комментарий |
|---|---|---|
| id | INTEGER PK | |
| message_id | INTEGER FK | |
| original_name | TEXT | имя, которое видит пользователь |
| storage_path | TEXT | `2026\08\{uuid}.bin` |
| size | INTEGER | |
| sha256 | TEXT | |
| state | TEXT | `uploading` / `ready` / `failed` / `orphaned` / `deleted` / `missing` |

Физический файл один на сообщение, даже если получателей пять. Копий на диске не плодим.

**Когда файл можно удалять.** Раз копия одна, а ссылок на неё несколько, удалять её по команде одного участника нельзя. Вложение становится ничейным, когда его скрыли **все**: и отправитель, и каждый получатель. Отдельный счётчик ссылок не заводим — он рано или поздно разойдётся с реальностью; состояние вычисляется запросом:

```sql
SELECT a.id FROM attachments a
JOIN messages m ON m.id = a.message_id
WHERE a.state = 'ready' AND m.deleted_by_sender = 1
  AND NOT EXISTS (
      SELECT 1 FROM message_recipients r
      WHERE r.message_id = m.id AND r.deleted_by_recipient = 0
  );
```

Найденное помечается `orphaned`. Такой файл уже недостижим через API ни для кого — он просто занимает место. Само по себе удаление всё равно не происходит: `orphaned` попадает в отчёт администратору и в предупреждение о свободном месте, а удаляется вручную либо флагом `delete_orphaned` (см. 2.6). После физического удаления строка не исчезает, а переходит в `deleted` — история переписки и аудит остаются целыми, пропадает только содержимое.

**upload_sessions**

| Поле | Тип | Комментарий |
|---|---|---|
| id | TEXT PK | uuid |
| attachment_id | INTEGER FK | |
| total_size | INTEGER | |
| chunk_size | INTEGER | |
| received_chunks | TEXT | JSON-массив номеров |
| updated_at | TEXT | |
| state | TEXT | `active` / `stale` / `committed` — влияет на резервирование места, см. 2.7 |

**events** — журнал изменений, по которому синхронизируются клиенты

| Поле | Тип | Комментарий |
|---|---|---|
| id | INTEGER PK AUTOINCREMENT | монотонный курсор — тот самый `since` |
| station_id | INTEGER FK | **какой станции** адресовано событие |
| type | TEXT | `new_message` / `read` / `downloaded` / `deleted` |
| object_id | INTEGER | id сообщения |
| created_at | TEXT | |

Строка пишется на каждого адресата: отправка письма пяти станциям — пять строк `new_message`, а когда получатель нажал «скачать», появляется одна строка `downloaded` для отправителя. Клиент хранит у себя `last_event_id` и спрашивает `GET /api/events?since={last_event_id}` — сервер отдаёт строки с бо́льшим `id`, адресованные этой станции.

Два неочевидных момента, которые ломают синхронизацию, если их пропустить:

- **`AUTOINCREMENT` обязателен.** Без него SQLite после удаления строк переиспользует освободившиеся `id`, и клиент с курсором на старом значении молча пропустит новые события. Ключевое слово стоит лишних байт на строку и снимает целый класс невоспроизводимых багов.
- **Курсор проверяется с двух сторон.** События старше 30 дней подчищаются, иначе таблица растёт вечно. Если пришедший `since` **меньше минимального** `id` — станция не была в сети дольше срока хранения, и догонять по событиям нечего. Если `since` **больше максимального** — значит журнал на сервере откатился назад, а это ровно то, что происходит после восстановления БД из резервной копии (см. 2.13). Оба случая обрабатываются одинаково: сервер отвечает `{"resync_required": true}`, клиент перечитывает входящие целиком через `/api/inbox` и берёт свежий курсор. Без второй проверки станция после восстановления замолчала бы навсегда — её курсор недостижим, и новых событий она не увидит уже никогда.

**audit_log** — station_id, action, object_id, details, timestamp.

`events` и `audit_log` намеренно разведены, хотя выглядят похоже. Аудит пишется от лица той станции, **которая** совершила действие, нужен службе безопасности и не чистится никогда. `events` адресован той, **которой** об изменении нужно узнать, и живёт 30 дней. Если свести их в одну таблицу, клиенты будут листать через записи о входах администратора, а аудит станет невозможно обрезать.

### 2.4 API

Авторизация: заголовок `Authorization: Bearer {token}` на всех запросах, кроме регистрации станции и получения токена.

**Аутентификация и справочники**
```
POST /api/stations/register   {enrollment_code, display_name, machine_name, client_version}
                              → {station_id, secret} — один раз при установке
POST /api/auth/token          {station_id, secret, client_version} → {token, expires_at, station}
GET  /api/directory           список станций: имя, присутствие, версия — он же адресная книга
GET  /api/me                  своя карточка
PATCH /api/me                 {display_name} — смена отображаемого имени
```

Формы входа у пользователя нет: клиент получает токен по ключу станции сам, при запуске. Это прямое следствие того, что адресат — станция, и главная причина, по которой человеку не приходится ничего вводить.

**Администрирование** — доступно только при `is_admin`. Отдельного приложения и веб-панели нет: эти вызовы обслуживают дополнительные разделы того же клиента (см. 3.8), а для первого запуска есть консольная утилита на сервере (см. 2.11).
```
GET    /api/admin/stations           все станции, включая деактивированные
POST   /api/admin/enrollment         → {enrollment_code, expires_at} — одноразовый код на установку
PATCH  /api/admin/stations/{id}      переименовать, деактивировать, выдать/снять админа
POST   /api/admin/stations/{id}/reset  отозвать ключ станции, выдать новый код регистрации
GET    /api/admin/storage            занято, свободно, список orphaned и старых файлов
DELETE /api/admin/attachments/{id}   удалить содержимое, строку оставить (state = deleted)
GET    /api/admin/audit?from=&to=&station=   выгрузка журнала
GET    /api/admin/settings           текущий config.toml
PATCH  /api/admin/settings           правка параметров с пометкой «горячий», см. 2.6
```

**Отправка**
```
POST /api/messages                          {subject, body, recipients[]} → {message_id}
POST /api/messages/{id}/attachments/init    {name, size, sha256} → {attachment_id, upload_id, chunk_size}
                                            507 Insufficient Storage, если места нет с учётом резерва
PUT  /api/uploads/{upload_id}/chunk/{n}     сырое тело запроса, поток на диск
GET  /api/uploads/{upload_id}/status        → {received_chunks[]} — для докачки после обрыва
POST /api/uploads/{upload_id}/commit        → 202 Accepted; сборка, сверка sha256 и перенос
                                            идут фоном, готовность — по state вложения
POST /api/messages/{id}/send                перевод из draft в sent
```

**Получение**
```
GET  /api/inbox?since={event_id}      входящие
GET  /api/sent                        отправленные
GET  /api/messages/{id}               карточка сообщения со списком вложений
GET  /api/attachments/{id}/download   поддержка заголовка Range
POST /api/messages/{id}/read          отметка «прочитано»
POST /api/messages/{id}/ack           отметка «вложения скачаны»
DELETE /api/messages/{id}             скрыть у себя
```

**Синхронизация**
```
GET  /api/events?since={event_id}     → {events[], last_event_id}
                                      либо {resync_required: true}, если курсор протух
GET  /api/health                      состояние сервера, свободное место
```

### 2.5 Жизненный цикл передачи

```
Отправитель                    Сервер                      Получатель
    │                            │                              │
    ├─ POST /messages ──────────►│  создан draft                │
    ├─ attachments/init ────────►│  выделен upload_id           │
    ├─ PUT chunk 0 ─────────────►│  ┐                           │
    ├─ PUT chunk 1 ─────────────►│  │ пишутся в tmp\            │
    │       ... (обрыв связи)    │  │                           │
    ├─ GET uploads/status ──────►│  │ вернул принятые чанки     │
    ├─ PUT chunk 7..N ──────────►│  ┘ докачка с нужного места   │
    ├─ POST commit ─────────────►│  202: принято, сборка фоном  │
    │◄─ статус: ready ───────────┤  сверка sha256 → rename      │
    ├─ POST send ───────────────►│  status = sent               │
    │                            │  events: +1 строка на адресат│
    │                            │◄──── GET /events ────────────┤
    │                            │      уведомление в трее      │
    │                            │◄──── GET /download (Range) ──┤
    │                            │◄──── POST /ack ──────────────┤
    │◄── статус «скачано» ───────┤                              │
```

Состояние получателя: `новое` → `прочитано` → `скачано`. Отправитель видит все три — это снимает вечный вопрос «я тебе отправлял, ты получил?».

### 2.6 Конфигурация (config.toml)

```toml
[server]
host = "0.0.0.0"
port = 8080
token_ttl_hours = 12
presence_timeout_sec = 45      # после какого молчания станция считается не в сети, см. 2.10
min_client_version = "1.0.0"   # клиенты старее получают понятный отказ, а не странные ошибки
discovery_enabled = false      # UDP-ответчик для автопоиска, см. 2.9
discovery_port = 8081

[storage]
path = "D:\\FilePost\\storage"
tmp_path = "D:\\FilePost\\tmp"
chunk_size_mb = 16
min_free_space_gb = 50        # ниже этого порога приём новых файлов блокируется
max_file_size_gb = 20

[retention]
enabled = false                # ПО УМОЛЧАНИЮ ВЫКЛЮЧЕНО — ничего не удаляется само
delete_after_download_days = 7
delete_never_downloaded_days = 30
notify_sender_before_days = 2
delete_orphaned = false        # файлы, которые скрыли у себя все участники (см. 2.3)

[cleanup]
abandoned_uploads_hours = 48   # уборка недокачанного мусора из tmp\, работает всегда
reservation_idle_hours = 2     # через сколько простоя сессия перестаёт держать резерв места
events_retention_days = 30     # обрезка журнала событий, на пользовательские файлы не влияет

[backup]
enabled = true                 # бэкап БД, а не файлов — см. 2.13
path = "E:\\Backup\\FilePost"  # ОБЯЗАТЕЛЬНО другой физический диск
time = "03:00"
keep_copies = 14

[limits]
max_parallel_uploads_per_user = 2
max_parallel_downloads_per_user = 2   # иначе пятеро получателей одного письма кладут диск
max_recipients_per_message = 20
max_attachments_per_message = 50
```

**Что применяется на лету, а что требует перезапуска.** Администратор правит эти параметры из раздела «Сервер» в клиенте (см. 3.8), и подпись рядом с полем должна быть честной — иначе изменение молча не сработает:

| Параметр | Применение |
|---|---|
| Пороги и сроки: `min_free_space_gb`, `max_file_size_gb`, весь `[retention]`, весь `[cleanup]`, весь `[limits]`, `presence_timeout_sec`, `min_client_version` | сразу |
| `token_ttl_hours` | сразу, но на уже выданные токены не влияет |
| `chunk_size_mb` | сразу для новых загрузок; идущие продолжаются со своим размером |
| `host`, `port`, пути хранилища, `discovery_*` | после перезапуска службы |

Правило простое: числа и флаги подхватываются на лету, всё, что связано с открытием сокетов и файловых путей, — нет. Смена `chunk_size_mb` посреди активных заливок безопасна именно потому, что размер чанка зафиксирован в `upload_sessions` при `init`, а не берётся из конфига каждый раз.

**Про удаление.** Автоочистка выключена по умолчанию и включается одним флагом, если заказчик передумает. Вместо неё в системе есть:

- предупреждение администратору при падении свободного места ниже порога;
- страница/CLI-команда «показать всё старше N дней» с ручным выбором и удалением;
- там же — список `orphaned`: файлы, которые все участники уже скрыли у себя. Это первое, что стоит удалять при нехватке места: они никому не видны, и никто не заметит пропажи;
- отдельная уборка `tmp\` — это не пользовательские данные, а мусор от оборванных загрузок, и её отключать смысла нет.

При всём этом надо понимать: с выключенным `retention` и выключенным `delete_orphaned` диск заполняется монотонно и никогда не освобождается сам. Единственный тормоз — администратор, пришедший по предупреждению. Для 7 станций это рабочая схема на годы, но предупреждение о свободном месте перестаёт быть перестраховкой и становится обязательным элементом.

### 2.7 Надёжность

- Чанки пишутся **потоком на диск**, файл целиком в память не поднимается никогда.
- Перемещение в `storage\` атомарное; запись в БД `state = ready` — после успешного перемещения. Файл либо есть целиком, либо его нет.
- SQLite в WAL — параллельное чтение не блокируется записью.

**Контрольная сумма и цена `commit`.** Хеш всего файла нельзя досчитывать по мере приёма чанков: они приходят не по порядку, а после обрыва часть заливается заново. Поэтому распределение обязанностей такое:

| Кто | Когда | Что считает |
|---|---|---|
| Клиент | при чтении файла с диска, до или во время отправки | SHA-256 целого файла, уходит в `init` |
| Сервер | на `commit`, при сборке чанков по порядку | SHA-256 собранного файла, сверяется с заявленным |
| Обе стороны | на каждый чанк (опционально) | CRC32 — ловит битый чанк сразу, а не в конце |

Отсюда практическое следствие, которое надо заложить и в сервер, и в интерфейс: **`commit` не мгновенный**. Для файла в 5 ГБ это чтение 5 ГБ с диска, то есть от единиц до десятков секунд. Запрос не должен держать блокировку БД и не должен упираться в HTTP-таймаут клиента: сборка идёт фоновой задачей, `commit` сразу отвечает «принято», а готовность клиент видит по статусу вложения. В окне передач это отдельная фаза «Проверка», иначе пользователь смотрит на замерший на 100% прогресс и жмёт «Отменить».

Если сборка окажется узким местом, чанки можно писать не отдельными файлами, а сразу в один разреженный файл со смещением `n × chunk_size` — тогда конкатенация не нужна вовсе и остаётся только проход для хеша. На старте не усложняем: отдельные чанки проще чинить после сбоя.

**Резервирование места.** Проверять на `init` только `free_space` недостаточно — проверка гоночная. Семь станций по две параллельные заливки до 20 ГБ каждая дают до 280 ГБ: все получат «место есть» одновременно и вместе забьют диск. Поэтому на `init` считается доступный объём **за вычетом уже обещанного**:

```
free_space − Σ(total_size − uploaded_bytes) по активным сессиям − size ≥ min_free_space_gb
```

Не проходит — сразу `507`, а не отказ на середине заливки. Резерв освобождается при `commit`, при отмене и при переходе сессии в `stale` — если по ней не было ни одного чанка `reservation_idle_hours`. Таймеров здесь два, и это не дублирование: резерв отпускается через 2 часа простоя, чтобы брошенная сессия не держала место, а сами файлы в `tmp\` живут до 48 часов — на случай, если пользователь всё-таки вернётся и продолжит докачку.

### 2.8 Безопасность

- Папка `storage\` — NTFS-права только на служебную учётку службы, группе «Пользователи» явный `deny`. Добраться до файлов можно **исключительно через API с токеном**. Формально и по сути это не сетевая папка.
- Имена файлов на диске — UUID. Оригинальное имя живёт только в БД, значит path traversal через имя невозможен в принципе.
- Ключи станций — bcrypt или argon2, токены с ограниченным сроком. Ключ хранится на станции и по сети не передаётся: в запросе уходит только он сам при получении токена, дальше работает Bearer-токен с TTL.
- Станцией в системе можно стать только по одноразовому коду от администратора. Скомпрометированную станцию отзывают одной командой, старый ключ умирает немедленно.
- Полный аудит-журнал: какая станция, кому, что и когда передала, кто и когда забрал.
- Обратная сторона отсутствия входа: кто сел за включённый ПК, тот видит почту этой станции. Компенсируется блокировкой экрана и физическим контролем помещения — подробнее в 2.10.
- Открывается **один порт** вместо 445-го. С точки зрения ИБ это выигрышнее шары, и на этом стоит строить разговор с теми, кто запрет вводил.

### 2.9 Адресация и обнаружение сервера

Клиент находит сервер по адресу из `config.ini`, который прописывается при развёртывании — пользователь его не вводит и не выбирает. Автопоиска в базовой схеме нет намеренно: восемь машин в плоской сети не тот масштаб, ради которого стоит заводить лишний протокол.

Предусловие у этого одно, но жёсткое: **у сервера фиксированный адрес**. Статический IP либо резервация по MAC на DHCP. Если адрес однажды сменится сам, связь потеряют разом все семь станций, и лечиться это будет обходом машин руками.

**Порядок разрешения адреса при старте клиента**

```
config.ini: url ─────────► GET /api/health (таймаут 5 с)
     │ нет ответа
     ▼
config.ini: fallback ────► GET /api/health
     │ нет ответа
     ▼
UDP-broadcast discovery (если включён в конфиге)
     │ нет ответа
     ▼
офлайн-режим: локальная БД + баннер «нет связи с сервером»,
исходящие копятся в очереди (см. 3.6)
```

Ни на одном шаге клиент не блокируется и не показывает модальное окно с ошибкой. Адрес, найденный через discovery, записывается в `config.ini` и на следующем старте проверяется первым.

**Клиентский конфиг**

```ini
[server]
url         = http://filepost-srv:8080
fallback    = http://10.10.10.5:8080    ; если имя не резолвится
timeout_sec = 5
discovery   = false                      ; UDP-поиск как крайняя мера
```

**Имя или IP.** Голый IP работает всегда и ни от чего не зависит, но переезд сервера означает обход всех станций. Имя (`filepost-srv`) от этого избавляет: в домене оно резолвится через DNS само, без домена — строкой в `C:\Windows\System32\drivers\etc\hosts` на каждой машине:

```
10.10.10.5    filepost-srv
```

Работа та же ручная, но раскатывается логон-скриптом или GPO централизованно, а при переезде правится одна строка вместо конфига приложения. На NetBIOS/mDNS без домена полагаться не стоит — резолвится через раз. Отсюда и схема выше: имя основным адресом, IP запасным.

**UDP-автопоиск** (опционально, по умолчанию выключен с обеих сторон):

| Шаг | Действие |
|---|---|
| 1 | Клиент шлёт broadcast на `255.255.255.255:8081`, тело `FILEPOST_DISCOVER_V1` |
| 2 | Сервер отвечает юникастом `FILEPOST_SERVER_V1 http://10.10.10.5:8080` |
| 3 | Клиент сохраняет адрес в `config.ini` и дальше ходит напрямую |

Ограничения, из-за которых это именно запасной путь, а не основной: broadcast не проходит между подсетями (здесь сеть плоская — не мешает), нужно отдельное правило брандмауэра на UDP 8081, и ответ ничем не подписан — любая машина в сети может ответить первой и увести на себя чужие файлы. Ключ станции при этом не утекает: он не передаётся, а проверяется сервером, так что подставной сервер получит только то, что ему отправят после подмены. Ущерб всё равно реальный, поэтому discovery включается только когда адреса нет вовсе, и найденный адрес сразу фиксируется в конфиге.

**Сеть и брандмауэр.** На сервере — правило на входящий TCP 8080, ограниченное подсетью предприятия:

```
netsh advfirewall firewall add rule name="FilePost HTTP" dir=in action=allow ^
  protocol=TCP localport=8080 remoteip=10.10.10.0/24 profile=any
```

`profile=any` здесь не перестраховка: сеть без домена и шлюза Windows обычно относит к «Общедоступной», а правило по привычке создают для «Частной» — и сервер молча не отвечает. Uvicorn при этом слушает `0.0.0.0`, а не `127.0.0.1`. На клиентах не требуется ничего: исходящие соединения разрешены по умолчанию.

### 2.10 Адресная книга станций и присутствие

Правило, из которого всё следует: **человек не вводит ни адресов, ни имён машин, ни логинов — никогда и нигде**. Всё, что можно выбрать из списка, выбирается из списка, а список приходит с сервера.

**Кому адресуется письмо.** Получатель — **станция**, то есть конкретный ПК с установленным клиентом. Не человек, не учётная запись. Клиент стоит на машине, у клиента есть имя, заданное в его настройках, и письма ходят между этими именами.

Из этого следует, что адресная книга и список машин с клиентом — **один и тот же список**, а не два связанных между собой. `GET /api/directory`:

```json
[ { "station_id": 4,
    "display_name": "Бухгалтерия, окно 2",
    "online": true,
    "last_seen_at": "2026-08-21T09:41:12Z",
    "client_version": "1.0.3" } ]
```

В выпадающем списке это одна строка: `Бухгалтерия, окно 2 · в сети`. Ни IP, ни `WKS-003`, ни логина в интерфейсе не появляется.

| Станция | Статус | Версия |
|---|---|---|
| Бухгалтерия, окно 2 | в сети | 1.0.3 |
| Склад | 40 минут назад | 1.0.3 |
| Кадры | не в сети с 19.08 | 1.0.1 |

Тот же список отвечает на вопросы, которые иначе решаются обходом кабинетов: где установлен клиент, кто сейчас на связи и где остался необновлённый `.exe`.

**Что из этого следует принять сознательно.** Почтовый ящик привязан к машине, а не к человеку:

- пересел за другой ПК — своей переписки там не увидишь, она осталась на прежней станции;
- если за одной машиной работают посменно двое, ящик у них общий;
- переезд сотрудника на другое рабочее место решается переименованием станций, а не переносом данных.

Для семи рабочих мест, где за каждым закреплён свой человек, это не ограничение, а упрощение: исчезает целый слой учётных записей, форма входа и всё, что с ней связано. Отправитель к тому же думает ровно так же — «отправить в бухгалтерию», а не «отправить учётной записи Иванова». Оговорить это с заказчиком стоит один раз и явно: если появится требование, чтобы почта следовала за человеком по машинам, поверх станций придётся вводить пользователей, и это уже другая система.

**Имя станции.** Задаётся в настройках клиента (см. 3.7), хранится на сервере, расходится по остальным станциям событием. По умолчанию подставляется имя ПК из Windows — `WKS-003`, `BUH-PC`: пустых строк в списках не бывает, но заменить это на «Бухгалтерия, окно 2» стоит при установке. Переименовать может сама станция или администратор для любой.

**Присутствие достаётся даром.** Отдельный протокол для «в сети» не нужен: клиент и так опрашивает `/api/events` раз в 10–15 секунд, и каждый такой запрос обновляет `last_seen_at`. В сети — значит `last_seen_at` моложе 45 секунд, то есть трёх пропущенных опросов подряд. Никакого heartbeat, никаких сокетов.

Показатель честный ровно настолько, насколько нужно: он означает «клиент запущен и видит сервер», а не «человек за столом». В интерфейсе поэтому пишется «в сети», а не «доступен», и рядом всегда стоит время последней активности.

**Как станция попадает в систему.** Регистрация одноразовым кодом, который администратор выдаёт при установке:

```
Администратор            Сервер                  Новая станция
     ├─ POST /admin/enrollment ─►│                      │
     │◄── код 4F2A-91C7 ─────────┤                      │
     │  код передаётся установщику или вводится вручную │
     │                           │◄─ POST /stations/register ─┤
     │                           │   {код, «Бухгалтерия, окно 2»}
     │                           ├── {station_id, secret} ───►│
     │                           │   ключ ложится в config.ini│
     │                           │◄─ POST /auth/token ────────┤
     │                           │   дальше клиент входит сам │
```

Код одноразовый и с коротким сроком жизни. Дальше клиент авторизуется своим ключом при каждом запуске и держит токен с TTL — человек формы входа не видит вообще.

Отсюда же берётся управляемость: посторонняя машина в сети не станет адресатом, не получив кода от администратора, а скомпрометированную станцию отзывают `POST /admin/stations/{id}/reset` — старый ключ перестаёт действовать немедленно.

**Про физический доступ надо сказать прямо.** Раз входа нет, всякий, кто сел за включённый ПК, видит переписку этой станции. Защита здесь — та же, что и у самой Windows: блокировка экрана и физический контроль помещения. Это осознанный размен: либо форма входа на каждом запуске клиента, либо её отсутствие. При семи машинах в закрытом контуре второе практичнее, но решение принимает заказчик, и в протокол встречи его лучше занести.

### 2.11 Администрирование и первый запуск

Веб-панели нет. Решение сознательное: в системе ровно два приложения — служба на сервере и клиент на станциях. Всё управление разнесено между ними так:

| Задача | Где делается |
|---|---|
| Станции, хранилище, аудит, настройки | Разделы клиента на административной станции (см. 3.8) |
| Регистрация первой станции, восстановление доступа, обслуживание БД | Консольная утилита `filepost-admin` на сервере |

Смысл разделения: повседневное администрирование делается из того же привычного окна, что и работа с почтой, а консоль остаётся для случаев, когда клиент недоступен в принципе.

**Первый запуск — задача про курицу и яйцо.** Код регистрации выдаёт администратор из клиента, но самого клиента ещё нет ни на одной машине. Разрывается это консолью: `init` создаёт БД и печатает первый код регистрации **один раз**, в консоль и в `logs\app.log`.

```
> filepost-server init
База данных создана: D:\FilePost\db\filepost.db
Код регистрации первой станции: 4F2A-91C7-DE38
Станция получит права администратора. Код действует 24 часа и только один раз.
```

Первая зарегистрированная по нему станция получает `is_admin` — это рабочее место администратора, откуда выдаются коды остальным. Ограничение по времени и однократность здесь важнее удобства: код, оставшийся в журнале развёртывания, к моменту эксплуатации уже недействителен.

**Консольные команды на сервере:**

```
filepost-server init                       создание БД и кода для первой станции
filepost-admin station list                все станции, статус, версия клиента
filepost-admin station enroll <имя>        выдать код регистрации новой станции
filepost-admin station reset <имя>         отозвать ключ, выдать новый код
filepost-admin station admin <имя>         выдать или снять права администратора
filepost-admin storage report              занято, свободно, orphaned, старые файлы
filepost-admin storage verify              сверка БД и диска: записи без файлов и наоборот
filepost-admin db backup <путь>            корректный бэкап живой базы (не копирование файла)
filepost-admin db verify <файл>            проверка резервной копии на читаемость
```

`station reset` и `station admin` — выход из положения, когда административная станция вышла из строя или переустановлена: без консоли выдать права было бы некому, и система осталась бы без управления. Доступ к серверу у администратора и так есть, так что это не новая привилегия, а страховка.

**Права.** Проверка `is_admin` — на стороне сервера, на каждом `/api/admin/*`. Обычный клиент админские разделы просто не показывает, но это удобство интерфейса, а не защита: подделанный клиент получит от сервера `403`.

**Действия администратора пишутся в тот же `audit_log`** и ничем не привилегированы. Выдача кодов, отзыв ключей, удаление файлов — всё видно, включая станцию, с которой это сделано. При этом администратор **не может читать чужую переписку**: в API нет endpoint'а, отдающего чужое сообщение или вложение. Видны факты передачи — кто, кому, когда, какого размера, забрали или нет, — но не содержимое. Проговорить это с заказчиком стоит отдельно: вопрос «а начальник сможет читать мои файлы?» возникает всегда.

### 2.12 Восстановление после сбоя

Службу может убить что угодно: перезагрузка сервера по питанию, падение процесса, остановка администратором посреди работы. Опасны здесь не сами сбои, а промежутки между двумя действиями, которые должны были случиться вместе.

Таких промежутков ровно столько, сколько мест, где файл на диске и запись в БД меняются не одновременно. Поэтому **при каждом старте служба прогоняет процедуру восстановления** и только потом начинает принимать запросы:

| Что могло сломаться | Как обнаружить | Что делать |
|---|---|---|
| Сборка прервана на середине | `upload_sessions.state = 'committed'`, а вложение всё ещё `uploading` | собрать заново из чанков в `tmp\`, сверить sha256, перенести |
| Файл перенесён, БД не обновлена | вложение `uploading`, но файл лежит по `storage_path` | сверить sha256, поставить `ready` |
| Запись `ready` без файла на диске | сверка при `storage verify` | пометить `missing`, сообщить отправителю и получателям |
| Файл на диске без записи в БД | та же сверка | в отчёт администратору, удаление вручную |
| Резерв места «завис» после падения | ничего не нужно обнаруживать | пересчитывается из `upload_sessions` при старте |

Три вещи делают эту таблицу короткой, а не бесконечной.

**Порядок операций всегда один: сначала диск, потом БД.** Файл переносится в `storage\`, и только после успешного переноса пишется `state = ready`. Обратный порядок дал бы запись, указывающую в пустоту, — а это отправитель, уверенный, что файл доставлен, и получатель, скачивающий ошибку. Лишний файл на диске без записи безобиднее: он не виден никому и находится сверкой.

**Сборка идемпотентна.** Чанки лежат в `tmp\` до самого конца, поэтому повтор сборки после падения — это просто повтор, а не восстановление по обломкам. Промежуточный файл получает отдельное имя и удаляется перед новой попыткой, так что недособранный кусок не может быть принят за готовый.

**Резерв места нигде не хранится отдельно.** Он вычисляется из активных сессий (см. 2.7), то есть живёт в той же БД, что и всё остальное. Падение службы его не теряет и не «подвешивает» — после старта он просто пересчитывается. Если бы резерв держался в памяти, каждый перезапуск требовал бы отдельного механизма его восстановления.

**Со стороны станций ничего делать не нужно.** Клиент, у которого оборвалась заливка, запрашивает `/uploads/status` и продолжает с недостающего чанка — сбой сервера для него неотличим от обрыва сети. Вложение, ушедшее в `failed`, превращается в «Ошибка проверки, повторить».

Это работает потому, что весь API идемпотентен по построению: повторный `PUT` того же чанка перезаписывает его, повторный `commit` на готовом вложении отвечает успехом, повторный `send` не создаёт второго сообщения. В сети, где соединение может оборваться в любой момент, «отправил и не знаю, дошло ли» — нормальное состояние клиента, и единственный дешёвый ответ на него — сделать повтор безопасным.

**SQLite восстанавливается сам.** WAL накатывается при открытии базы, вмешательства это не требует. Единственное правило: не удалять файлы `-wal` и `-shm` руками, они часть базы, а не мусор.

Результат прогона пишется в `app.log` и в аудит: сколько вложений досбирано, сколько помечено `missing`. Молча чинить и молча не чинить одинаково плохо — администратор должен видеть, что после падения система разобралась сама.

### 2.13 Резервное копирование

Три части системы стоят совершенно разного и защищаются по-разному:

| Что | Объём | Ценность | Как защищаем |
|---|---|---|---|
| `db\filepost.db` | мегабайты | вся история, реестр станций, ключи | ежедневный бэкап на другой диск |
| `config.toml` | килобайты | настройки развёртывания | туда же, вместе с БД |
| `storage\` | терабайты | транзитные файлы | **не бэкапим**, зеркалим диск |

**Сколько это места на самом деле.** Вопрос «а не съест ли бэкап весь диск» возникает первым, поэтому цифры сразу. Копируется только БД, а в ней нет ни байта самих файлов — лишь строки о них:

| Что накапливается за год | Оценка |
|---|---|
| Сообщения с темой и комментарием, ~50 в день | ~4 МБ |
| Строки получателей и вложений | ~7 МБ |
| Аудит-журнал (не чистится никогда) | ~20 МБ |
| События (живут 30 дней) | меньше мегабайта |
| **Итого база за год** | **30–50 МБ** |

Четырнадцать ежедневных копий такой базы — **меньше гигабайта**. На фоне хранилища в несколько терабайт это доли процента, и никакой экономии на отказе от бэкапа не выйдет: экономить тут просто не на чем.

Оперативной памяти это тоже не стоит: и `VACUUM INTO`, и backup API копируют базу постранично, а не поднимают её целиком в память.

**Зачем при этом вообще бэкап, если файлы целы.** Затем, что без базы файлы бесполезны. На диске лежат `a3f2c1e4-….bin` — и всё. Какому сообщению принадлежит файл, как он назывался у отправителя, кто кому его послал, забрали его или нет, какой у него sha256 — это знает только БД. Потеряли её: терабайты сохранились и превратились в анонимную кучу, разобрать которую нельзя в принципе. Вдобавок пропадает реестр станций с их ключами, то есть все семь рабочих мест надо регистрировать заново, а вся история переписки исчезает.

Отсюда и весь смысл: **50 мегабайт защищают несколько терабайт от превращения в мусор**. Дешевле страховки в этой системе нет.

**Файлы не бэкапятся, и это решение, а не упущение.** Хранилище — транзит: у отправителя оригинал остался, система его переносит, а не архивирует. Копировать терабайты некуда и незачем. Защита здесь другая — зеркальный том (RAID-1) на хранилище: он спасает от смерти диска, то есть от единственного сценария, который здесь реально грозит.

Подменять одно другим нельзя, и путать эти две вещи опасно: **RAID — не резервная копия**. Он не спасает ни от удаления, ни от порчи данных, ни от ошибки администратора, потому что честно повторяет их на обоих дисках. Поэтому у БД настоящий бэкап, а у хранилища зеркало — каждому своё.

Заказчику это надо проговорить прямо: **система не является архивом**. Если файл нужен через год, его хранят у себя, а не рассчитывают достать из FilePost. Ожидание «мы же вам всё отправили, у вас всё лежит» возникает само и обходится дорого.

**Базу нельзя просто скопировать.** В режиме WAL часть данных лежит в `-wal`, и копия файла на ходу почти гарантированно окажется битой — причём выяснится это в момент восстановления, когда уже поздно. Правильных способов два: `VACUUM INTO` или backup API SQLite (в Python это `Connection.backup()`), оба снимают согласованный снимок живой базы **без остановки службы**.

```
filepost-admin db backup E:\Backup\FilePost\filepost-2026-08-21.db
filepost-admin db verify  E:\Backup\FilePost\filepost-2026-08-21.db
```

Расписание — раз в сутки ночью, хранить две недели копий, писать **на другой физический диск**. Бэкап рядом с оригиналом защищает ровно от одного сценария — случайного удаления — и бесполезен ровно в том, ради чего его делают.

`db verify` гоняет `PRAGMA integrity_check` по свежей копии. Копия, которую ни разу не проверяли и не пробовали открыть, резервной копией не является — это файл, про который приятно думать, что он поможет.

**Восстановление.** Порядок такой:

```
1. Остановить службу
2. Положить копию БД на место filepost.db, удалить оставшиеся -wal и -shm
3. filepost-admin storage verify      ← обязательно, не пропускать
4. Запустить службу
5. Проверить список станций
```

Третий шаг обязателен, потому что **БД и хранилище после восстановления заведомо разъехались**. База — вчерашняя, файлы на диске — сегодняшние, и расхождение двустороннее:

- файлы, пришедшие после снятия копии, есть на диске, но их нет в БД — они невидимы и просто занимают место;
- файлы, удалённые после снятия копии, числятся в БД, но их нет на диске — вложения помечаются `missing`.

`storage verify` находит и то и другое, метит записи и выдаёт отчёт. Без этого шага система выглядит рабочей, а расхождение всплывает потом, у случайного человека, пытающегося скачать давно удалённый файл.

Пятый шаг — про станции, зарегистрированные после снятия копии: в восстановленной базе их нет, их ключи недействительны, и клиенты получат `401`. Лечится повторной регистрацией по новому коду. Ничего не сломается молча — станция просто скажет, что не может подключиться, — но знать об этом заранее лучше, чем разбираться по звонку.

Про клиентов же беспокоиться не нужно: их курсоры окажутся впереди журнала событий, сервер ответит `resync_required`, и они перечитают входящие целиком (см. 2.3). Именно ради этого случая проверка курсора сделана двусторонней.

### 3.1 Слои

```
┌─────────────────────────────────────────┐
│  UI  (PySide6)                          │
│  главное окно + иконка в трее           │
├─────────────────────────────────────────┤
│  Core                                   │
│  ├─ TransferManager  очередь, потоки    │
│  ├─ SyncAgent        опрос /events      │
│  ├─ Directory        люди и станции     │
│  ├─ LocalStore       SQLite + файлы     │
│  └─ Settings                            │
├─────────────────────────────────────────┤
│  ApiClient  (httpx)                     │
└─────────────────────────────────────────┘
```

Строго однонаправленная зависимость: UI ничего не знает про HTTP, Core ничего не знает про виджеты. Выгода здесь не в гипотетическом втором клиенте, а в том, что ядро проверяется автотестами без запуска окон, а очередь передач не размазывается по обработчикам кнопок.

### 3.2 Интерфейс

Три правила, которым подчинено всё остальное:

1. **Ничего не вводить руками.** Ни адреса сервера, ни имени машины, ни логина. Формы входа нет вовсе — клиент авторизуется ключом станции сам. Всё остальное выбирается из списков, которые приходят с сервера.
2. **Показывать человеческие имена.** «Бухгалтерия, окно 2», а не `10.10.10.7` и не `WKS-003`. Технические идентификаторы живут в разделе диагностики, и обычный пользователь их не видит за всё время работы.
3. **Говорить по-русски в ошибках.** Не `HTTP 507`, а «На сервере закончилось место, сообщите администратору». Пользователь не должен догадываться, что делать.

**Главное окно** — раскладка узнаваемая, как в почтовом клиенте:

```
┌──────────────┬─────────────────────────┬───────────────────────────┐
│ ✉ Входящие 3 │ Склад            10:42  │ От:   Склад               │
│ ➤ Отправленн.│ Акты за июль        📎2 │ Кому: Бухгалтерия, окно 2 │
│ ✎ Черновики  │─────────────────────────│ Тема: Акты за июль        │
│ ⇅ Передачи 1 │ Кадры            вчера  │ 21.08.2026 10:42          │
│ 🖥 Станции   │ Дистрибутив ПО      📎1 │───────────────────────────│
│              │─────────────────────────│ Проверьте, пожалуйста, до │
│              │ Директор        19.08   │ пятницы.                  │
│              │ Инструкции          📎3 │                           │
│              │                         │ Вложения (1,4 ГБ):        │
│              │                         │ 📎 akty.zip       1,2 ГБ  │
│              │                         │ 📎 opis.pdf       240 КБ  │
│              │                         │                           │

Нижняя строка состояния держит три факта, которые снимают половину обращений в поддержку: есть ли связь, как называется эта станция в чужих списках, сколько места осталось на сервере. Когда связь пропадает, кружок краснеет и появляется «Нет связи с сервером, попытка через 12 с» — вместо тишины и непонимания.

Собственное имя в строке состояния стоит не для красоты: когда человек спрашивает «а куда мне сказать отправить?», ответ должен читаться с экрана, а не выясняться у администратора.

**Новое сообщение** — получатели выбираются из адресной книги, набор с клавиатуры работает как фильтр по списку, а не как ввод адреса:

```
┌─ Новое сообщение ───────────────────────────────────────────┐
│ Кому: [Склад ×] [Кадры ×] [ + Добавить ]                    │
│       ┌───────────────────────────────────────────────┐     │
│       │ Поиск: бух▮                                   │     │
│       │ ● Бухгалтерия, окно 1            в сети       │     │
│       │ ● Бухгалтерия, окно 2            в сети       │     │
│       │ ○ Бухгалтерия, кассир            2 ч назад    │     │
│       └───────────────────────────────────────────────┘     │
│ Тема: [Акты за июль                                    ]    │

Кружок слева от имени — присутствие: закрашенный значит «клиент запущен и на связи». Это не запрет отправлять офлайн-получателю: модель почтовая, файл дождётся. Но отправитель сразу видит, заберут файл через минуту или после выходных, и не бежит спрашивать.

Оценка «примерно 2 мин» считается по фактической скорости прошлых передач, а не по номинальной скорости сети. Первое, что спрашивают при отправке гигабайтов, — «сколько ждать».

**Передачи** — при таких объёмах вкладка нужна не меньше «Входящих»:

```

│                                                             │

│   ██████░░░░░░░░░░░░░░░░░░  24 %   1,1 ГБ / 4,6 ГБ          │
│   Приостановлено                  [ Продолжить ] [ Удалить ]│
│                                                             │
│ ✓ opis.pdf → Склад         Доставлено, скачано 10:44        │
└─────────────────────────────────────────────────────────────┘
```

Фаза «Проверка контрольной суммы» здесь показана намеренно — это та самая сборка на сервере из 2.7. Без отдельной фазы пользователь видит замерший на 100 % индикатор и жмёт «Отменить» ровно перед успешным завершением.

**Станции** — тот же список, что и в адресной книге, только целиком и с подробностями: все машины с клиентом, присутствие, время последней активности, версия. Обычному пользователю он нужен редко, но именно его открывают с вопросом «а склад вообще подключён?».

**Прочее по мелочи, что заметно в работе:**

- Непрочитанные — жирным, счётчик на иконке в трее и в заголовке окна.
- Всплывающее уведомление Windows при новом письме; клик открывает сообщение.
- Размеры — «1,2 ГБ», а не «1288490188 байт». Время — «вчера, 15:20» и «19.08», а не ISO-8601.
- Закрытие окна сворачивает в трей и не прерывает передачи; выход — явный пункт меню, и при активных передачах он переспрашивает.

### 3.3 Локальное состояние

```
%LOCALAPPDATA%\FilePost\
├── client.db      кэш сообщений, состояние очереди передач, last_event_id
├── downloads\     куда сохраняются полученные файлы
├── partial\       незавершённые .part-файлы
├── logs\client.log
└── config.ini     параметры развёртывания и пользовательские настройки
```

Отображаемое имя здесь **не хранится** — оно живёт на сервере (см. 2.3), иначе на каждой станции был бы свой список имён.

### 3.4 Передача файлов

**Отправка.** Файлы уходят в очередь `TransferManager`, обрабатываются в отдельных потоках (не более 1–2 одновременно, иначе они просто делят один и тот же канал). SHA-256 целого файла считается на лету при чтении и уходит в `init`. При обрыве — запрос `/uploads/status`, докачка недостающих чанков, повторы с нарастающей паузой.

После последнего чанка передача не закончена: клиент шлёт `commit`, получает `202` и ждёт, пока вложение перейдёт в `ready` (см. 2.7). В окне передач это отдельная фаза **«Проверка»** с неопределённым прогрессом — на гигабайтах она занимает секунды и десятки секунд, и без неё пользователь видит зависший на 100% индикатор. Отказ по хешу здесь же превращается в «Ошибка проверки, повторить».

`init` может вернуть `507` — на сервере нет места с учётом чужих незавершённых заливок. Это не ошибка сети и повторять её с нарастающей паузой бессмысленно: задание встаёт на паузу с понятным текстом «На сервере нет места, обратитесь к администратору».

**Скачивание.** Файл пишется в `partial\` как `.part`, при обрыве продолжается с нужного байта через заголовок `Range`. После завершения сверяется SHA-256, файл переносится в `downloads\`, на сервер уходит `ack`.

**Переживание перезапуска.** Состояние очереди лежит в `client.db`, а не в памяти: закрыли приложение на середине пятигигабайтной заливки — после запуска она продолжится, а не начнётся заново.

### 3.5 Синхронизация

Опрос `GET /api/events?since={last_event_id}` раз в 10–15 секунд. Для восьми машин этого достаточно, WebSocket на старте не нужен — он добавляет проблем с переподключением больше, чем экономит трафика.

`last_event_id` хранится в `client.db` и обновляется **только после того, как полученные события применены к локальной БД**. Порядок здесь важен: сохранить курсор раньше — значит потерять события при падении клиента между двумя операциями. Повторно применённое событие безвредно, потерянное — это не пришедшее письмо.

Если сервер ответил `{"resync_required": true}` (машина не включалась дольше срока хранения журнала), клиент перечитывает `/api/inbox` целиком, замещает локальный список и берёт новый курсор из ответа.

Автоскачивание вложений — **настройка, по умолчанию выключена**. При гигабайтных файлах решение «забирать или нет» должен принимать человек.

**Черновик живёт только локально.** Незаконченное письмо лежит в `client.db`, серверу о нём ничего не известно: сообщение там создаётся в момент отправки, не раньше. Из этого следует главное — письмо можно начать составлять без связи, а если отправка не удалась, клиент предлагает убрать его в черновики вместо того, чтобы потерять набранный текст и список файлов.

Черновик хранит пути к файлам, а не сами файлы. Файл могли переместить или удалить за то время, пока письмо лежало недописанным, поэтому при открытии черновика недостающие показываются отдельной строкой «файл не найден», а не молча пропадают из списка.

### 3.6 Работа без сервера

Список сообщений читается из локальной БД, поэтому окно открывается мгновенно и что-то показывает даже при недоступном сервере. Сверху — баннер «нет связи с сервером», исходящие копятся в очереди и уходят сами, когда связь вернётся.

Адресная книга кэшируется вместе с сообщениями, поэтому письмо можно составить и офлайн: получатели выбираются из последнего известного списка, файлы встают в очередь, отправка происходит сама при появлении связи. Статусы присутствия в этом режиме показываются серыми — «данные от 09:41», чтобы никто не принял кэш за текущее состояние.

### 3.7 Настройки клиента

Настройки делятся на два вида, и это разделение важнее самого списка:

- **Параметры развёртывания** — задаются при установке, пользователю показываются серым с подписью «Задано администратором». Сюда попадает всё, чем можно сломать себе клиент.
- **Пользовательские предпочтения** — меняются свободно, на других не влияют.

```
┌─ Настройки ─────────────────────────────────────────────────┐
│ Эта станция                                                 │
│   Отображаемое имя  [Бухгалтерия, окно 2             ]      │
│                     Под этим именем вас видят остальные     │
│                     и на него отправляют файлы              │
│                                                             │

│   Папка загрузок    [D:\Обмен\Входящие      ] [Выбрать…]    │
│   [ ] Скачивать вложения автоматически                      │
│   [✓] Открывать папку после сохранения                      │
│   При совпадении имён:  (•) переименовать  ( ) заменять     │
│                                                             │
│ Передача                                                    │
│   Одновременных передач   [2 ▾]                             │
│   [ ] Ограничить скорость отдачи  [___] МБ/с                │
│                                                             │

│   [✓] Уведомлять о завершении передачи                      │

│                                                             │

│ Сервер                        🔒 Задано администратором     │
│   Адрес   filepost-srv:8080                                 │

│                                                             │
│ [ Диагностика… ]                        [ ОК ] [ Отмена ]   │
└─────────────────────────────────────────────────────────────┘
```

| Параметр | По умолчанию | Кто меняет |
|---|---|---|
| Отображаемое имя станции | имя ПК из Windows | пользователь, уходит на сервер |
| Папка загрузок | `%LOCALAPPDATA%\FilePost\downloads` | пользователь |
| Автоскачивание вложений | выключено | пользователь |
| Звук уведомлений | выключен | пользователь |
| Действие при совпадении имён | переименовать | пользователь |
| Одновременных передач | 2 | пользователь, потолок задаёт сервер |
| Ограничение скорости отдачи | выключено | пользователь |
| Уведомления, звук | включены, звук выключен | пользователь |
| Автозапуск, старт в трее | включены | пользователь |
| Адрес сервера и запасной | из установки | 🔒 развёртывание |
| Автопоиск сервера (UDP) | выключен | 🔒 развёртывание |
| Ключ станции | выдан при регистрации | 🔒 не показывается вовсе |
| Таймаут соединения | 5 с | 🔒 развёртывание |
| Интервал опроса событий | 15 с | 🔒 развёртывание |

Две настройки заслуживают отдельного слова.

**Автоскачивание выключено по умолчанию** — при гигабайтных файлах решение «забирать или нет» принимает человек, иначе диск станции забьётся тем, что ему прислали «на всякий случай».

**Ограничение скорости отдачи** выглядит лишним в гигабитной сети, но именно оно спасает, когда кто-то отправляет 20 ГБ в разгар рабочего дня и остальные начинают жаловаться на тормоза. Дешёвая настройка, к которой обращаются раз в полгода и очень вовремя.

Предел здесь **общий на все потоки, а не на каждую передачу**: ограничивать нужно канал. Иначе «не больше 20 МБ/с» при двух параллельных заливках означает 40, и настройка перестаёт значить то, что на ней написано. Считается по факту переданного: после каждого чанка смотрим, сколько времени он должен был занять при заданном пределе, и досыпаем разницу — так средняя скорость выходит на предел без дробления чанков. Ожидание разбито на короткие шаги, чтобы «Пауза» и «Отменить» срабатывали сразу, а не через минуту простоя на медленном пределе.

**Звук уведомления** проигрывается через `winsound` из стандартной библиотеки Windows. Это накладывает ограничение — только WAV, — зато избавляет от QtMultimedia, который раздул бы `.exe` в несколько раз ради одного короткого сигнала. Звук никогда не блокирует интерфейс и не роняет его: не проигрался — значит не проигрался.

**Диагностика** — отдельное окно, куда убрано всё техническое: IP сервера, версия клиента и сервера, идентификатор станции, время последней синхронизации, путь к журналу и кнопка «Скопировать сведения» — чтобы пользователь мог одним нажатием передать администратору всё нужное вместо описания «не работает».

### 3.8 Режим администратора

Отдельного приложения нет: на станции с `is_admin` в том же клиенте появляются дополнительные разделы. Остальные их не видят, а сервер в любом случае проверяет права сам — скрытие в интерфейсе это удобство, а не защита.

```
┌──────────────┬──────────────────────────────────────────────┐
│ ✉ Входящие   │  Станции                                     │
│ ➤ Отправленн.│  ┌────────────────────────────────────────┐  │
│ ⇅ Передачи   │  │ Бухгалтерия, окно 2  в сети     1.0.3  │  │
│ 🖥 Станции   │  │ Склад                2 ч назад  1.0.3  │  │
│ ─────────────│  │ Кадры                19.08      1.0.1  │  │
│ 🛠 УПРАВЛЕНИЕ│  │ Архив (старый ПК)    отключена  1.0.0  │  │
│  Станции     │  └────────────────────────────────────────┘  │
│  Хранилище   │  [ Добавить станцию ] [ Переименовать ]      │
│  Журнал      │  [ Сбросить ключ ] [ Отключить ]             │
│  Сервер      │                                              │
│              │  Добавить станцию → код 4F2A-91C7-DE38       │
│              │  Действует 24 ч, вводится один раз при       │
│              │  установке клиента на новом ПК.              │
└──────────────┴──────────────────────────────────────────────┘
```

| Раздел | Что в нём |
|---|---|
| **Станции** | Выдать код регистрации, переименовать, отозвать ключ, деактивировать, выдать права администратора. Здесь же присутствие и версия `.exe` |
| **Хранилище** | Занято и свободно, список `orphaned`, файлы старше N дней, удаление с подтверждением |
| **Журнал** | Аудит с фильтрами по дате и станции, выгрузка в CSV |
| **Сервер** | Просмотр и правка `config.toml`; «горячие» параметры применяются сразу, остальные помечены «после перезапуска службы» |

Раздел «Хранилище» — главный рабочий инструмент администратора, потому что автоочистка выключена и место освобождает человек:

```
┌─ Хранилище ─────────────────────────────────────────────────┐
│ Занято 1,7 ТБ из 2 ТБ · свободно 340 ГБ    ⚠ порог 50 ГБ    │
│                                                             │
│ Ничейные файлы (скрыты всеми участниками)      86 ГБ  [ ▸ ] │
│ Скачано получателями, старше 30 дней          214 ГБ  [ ▸ ] │
│ Никем не скачано, старше 30 дней               12 ГБ  [ ▸ ] │
│ Незавершённые загрузки в tmp\                   4 ГБ  [ ▸ ] │
│                                                             │
│ [ Обновить ]                          [ Удалить выбранное ] │
└─────────────────────────────────────────────────────────────┘
```

Порядок строк не случаен: сверху то, что удалять безопаснее всего. Ничейные файлы не видны уже никому, и их удаление никто не заметит. Всё удаление — с подтверждением и записью в аудит, содержимое пропадает, а история переписки остаётся.

**Чего администратор не может.** Прочитать чужое сообщение или скачать чужое вложение — таких endpoint'ов в API нет вовсе, и это не настройка, которую можно включить. Видны факты передачи: кто, кому, когда, сколько, забрали или нет. Вопрос «а начальник сможет читать мои файлы?» звучит при внедрении всегда, и отвечать на него лучше устройством системы, а не обещанием.

## 4. Развёртывание

**Сервер**
1. Статический IP или резервация по MAC на DHCP — от этого зависит вся адресация клиентов (см. 2.9). Делается первым, до всего остального.
2. Python 3.11+ в отдельном venv (или embeddable-сборка, чтобы не ставить Python в систему).
3. Служба через NSSM: автозапуск, перезапуск при падении.
4. Правило брандмауэра на входящий TCP 8080 — только для подсети предприятия, `profile=any`.
5. Исключение антивируса для `D:\FilePost\` — realtime-сканирование режет скорость в разы и может перехватить файл в момент сборки. Согласовать заранее.
6. Хранилище на SSD, по возможности зеркальный том: файлы не бэкапятся, и от смерти диска защищает только зеркало (см. 2.13).
7. `[backup]` в конфиге — путь **на другой физический диск**. Через неделю после запуска проверить, что копии появляются, и один раз прогнать `db verify`.
8. `filepost-server init` — создание БД и кода регистрации первой станции. Код показывается один раз и живёт 24 часа (см. 2.11).
9. Клиент на рабочее место администратора ставится первым: он регистрируется по этому коду, получает права и дальше выдаёт коды остальным.

**Клиент**
1. Сборка PyInstaller в один `.exe`.
2. Установка в `%LOCALAPPDATA%`, автозапуск через ключ реестра `Run`.
3. Адрес сервера и запасной адрес прописываются в `config.ini` при развёртывании — пользователю вводить ничего не нужно.
4. Если используется имя, а не IP: строка в `hosts` на каждой станции либо запись в DNS. Раскатывается логон-скриптом или GPO, руками по машинам ходить не обязательно.
5. Код регистрации вводится один раз — установщиком или администратором при развёртывании. Дальше клиент хранит выданный ключ и входит сам.
6. Название станции («Бухгалтерия, окно 2») задаётся тогда же. Не задали — в списках будет имя ПК: рабочий вариант, просто менее понятный.

**От пользователя не требуется ничего.** Ни логина, ни пароля, ни адреса сервера, ни имени машины: код регистрации вводится один раз при установке, всё остальное клиент получает от сервера сам. Это и есть проверка, что развёртывание сделано правильно — если человеку пришлось что-то напечатать, чтобы начать работать, значит шаг пропущен.

**Проверка после развёртывания.** С любой станции `curl http://filepost-srv:8080/api/health` должен вернуть состояние сервера. Не вернул — вопрос в разрешении имени или в брандмауэре, и разбирается это до установки клиентов, а не после.

## 5. Порядок реализации

| Этап | Содержание | Результат |
|---|---|---|
| 1 | Сервер: БД, `filepost-server init`, регистрация станций по коду, авторизация по ключу, чанковая загрузка, скачивание с Range | Проверяется через `curl`, клиент ещё не нужен |
| 2 | Сервер: события, реестр станций и присутствие — он же адресная книга | Есть чем наполнить списки в клиенте |
| 3 | Клиент: окно, входящие/отправленные, выбор станции-получателя, отправка и приём с прогрессом | Рабочий прототип для показа заказчику |
| 4 | Трей, уведомления, статусы доставки, докачка после перезапуска, настройки клиента | Версия для опытной эксплуатации |
| 5 | Режим администратора в клиенте, аудит, хранилище, восстановление после сбоя, бэкапы | Готово к передаче в эксплуатацию |
| 6 | Установщики, документация для пользователя и администратора | Сдача |

Отличие от первоначального плана в одном: регистрация станций переехала на первый этап. Раньше это стояло в «админ-панели» ближе к сдаче, но без неё нечем завести даже тестового адресата для проверки этапа 1 — а править БД руками на каждом прогоне никто не станет. Консольная команда закрывает вопрос сразу, а раздел в клиенте появляется позже как удобная надстройка над теми же вызовами API.

## 6. Осознанно отложено

- **Прямая передача ПК↔ПК** — вдвое быстрее, но требует, чтобы обе машины были включены, и ломает почтовую модель. Имеет смысл только если объёмы вырастут и минуты начнут иметь значение.
- **TLS** — внутри изолированной сети без интернета выигрыш невелик, а возня с собственным CA и распространением сертификатов заметная. Закладываем возможность включить позже.
- **Группы рассылки** («вся бухгалтерия») — понадобятся, когда станций станет больше десятка.
- **Учётные записи людей поверх станций** — если появится требование, чтобы почта следовала за человеком с машины на машину (см. 2.10). Это не доработка, а смена модели адресации, и браться за неё стоит только по явному требованию заказчика.

**Веб-интерфейса не будет.** Это не отложенное решение, а принятое: в системе ровно два приложения — служба на сервере и клиент на станциях. Администрирование делается из того же клиента под учёткой администратора (3.8), первый запуск и восстановление доступа — консольной утилитой на сервере (2.11). Веб-панель означала бы третью кодовую базу, отдельную аутентификацию в браузере и сессии — при семи станциях это не окупается.
