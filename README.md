# FilePost

Система обмена файлами в закрытой сети: 7 рабочих станций + сервер, Windows 10,
без выхода в интернет, общие сетевые папки запрещены. Файлы — до нескольких гигабайт.

Модель работы — почтовая: адресная передача, а не общее хранилище. Отправитель заливает
файл на сервер, сервер хранит его, пока получатель не заберёт. Получатель может быть
выключен в момент отправки — это и есть главное отличие от прямой передачи.

## Ключевое решение

**Адресат — станция, а не человек.** Клиент установлен на конкретном ПК, у клиента есть
имя, заданное в его настройках, и письма ходят между этими именами. Отдельной сущности
«пользователь» в системе нет.

Отсюда следует то, ради чего всё и делалось: **человек не вводит ничего**, кроме кода
регистрации один раз при установке. Ни логина, ни пароля, ни адреса сервера, ни имени
машины. Формы входа нет вообще — клиент авторизуется ключом станции сам.

Обратная сторона, которую нужно принять сознательно: почтовый ящик привязан к машине.
Пересел за другой ПК — своей переписки там не увидишь. Подробности и обоснование —
в разделе 2.10 архитектуры.

## Быстрый старт

```bash
# сервер
cd server
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m filepost.cli --config config.toml init    # покажет код регистрации
.venv/bin/python -m filepost.cli --config config.toml serve

# клиент
cd ../client
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m filepost_client.main
```

При первом запуске клиент попросит адрес сервера, код регистрации и название станции
(«Бухгалтерия, окно 2»). Дальше он работает сам.

## Установщики

**Ставить ничего не нужно — ни Python, ни Inno Setup.** Сборка идёт на Windows-раннере
GitHub, готовые установщики скачиваются оттуда.

### Как получить

1. Вкладка **Actions** → последняя успешная сборка → раздел **Artifacts** →
   `FilePost-installers`.
2. Либо создать релиз тегом — тогда установщики появятся на вкладке **Releases**:

```bash
git tag v1.0.0 && git push --tags
```

Сборка гоняет тесты обоих компонентов и **проверяет собранный сервер вживую**:
запускает его и дёргает `/api/health`. Собранный exe умеет падать на том, чего
не видит статический анализ импортов, — тесты этого не ловят.

### Как ставить

**Сервер** — `FilePost-Server-Setup-1.0.0.exe` от имени администратора. Один
установщик делает всё: кладёт службу, генерирует `config.toml` под выбранный
каталог, регистрирует службу через NSSM, открывает порт 8080, заводит исключение
Defender и **показывает код регистрации первой станции**. Код показывается один
раз — запишите его.

**Клиент** — `FilePost-Setup-1.0.0.exe` на каждую станцию. Прав администратора
не требует, ставится в `%LOCALAPPDATA%`. При первом запуске спросит код регистрации.

Тихая установка с предзаданным адресом сервера — тогда пользователю останется
ввести только код:

```
FilePost-Setup-1.0.0.exe /VERYSILENT /SERVER=filepost-srv:8080 /STATION="Бухгалтерия, окно 2"
```

**На целевых машинах Python не нужен ни на сервере, ни на станциях.**

### Сборка у себя

Если нужно собрать локально, на машине с Python 3.11+ и Inno Setup 6:

```
build.cmd
```

Собирать можно **только на Windows**: PyInstaller не умеет кросс-компиляцию.

## Тесты

```bash
cd server && python -m pytest tests/ -q     # 86
cd client && python -m pytest tests/ -q     # 62
```

Клиентские тесты поднимают настоящий сервер в потоке и гоняют полный цикл: передачу,
докачку после обрыва, переживание перезапуска, пересинхронизацию после отката БД
сервера, работу без связи. Тесты интерфейса идут на offscreen-платформе Qt.

## Что реализовано

- Чанковая загрузка с докачкой после обрыва, скачивание с `Range`
- Резервирование места: проверка учитывает уже обещанное незавершённым заливкам
- SHA-256 на обеих сторонах, фоновая сборка с отдельной фазой «Проверка» в интерфейсе
- Восстановление при старте службы во всех трёх точках разрыва «диск ↔ БД»
- Журнал событий с двусторонней проверкой курсора, аудит-журнал
- Планировщик: уборка `tmp\`, обрезка событий, ночной бэкап с ротацией
- Резервное копирование живой базы в режиме WAL, сверка БД с диском
- Отзыв письма, пока получатели его не забрали
- Ограничение параллельных скачиваний и валидация ввода
- Клиент: трей, уведомления со звуком, очередь передач в SQLite, ограничение скорости
  отдачи и приёма, оценка времени по фактической скорости, локальные черновики,
  работа без сервера, админские разделы под учётной записью администратора

## Что осознанно не делается

- **Веб-интерфейса не будет.** В системе ровно два приложения: служба и клиент.
- **Прямая передача ПК↔ПК** — вдвое быстрее, но ломает почтовую модель.
- **TLS** — внутри изолированной сети выигрыш невелик, закладываем возможность включить.
- **Автоочистка выключена по умолчанию** — ничего не удаляется само.
