# FilePost — серверная часть

Реализация серверной части по `architecture (1).md`: БД, регистрация станций по коду,
авторизация ключом станции, чанковая загрузка с докачкой, скачивание с `Range`,
события и адресная книга, восстановление после сбоя, планировщик, резервное копирование.

Клиент — в каталоге `../client`.

## Установка

```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
```

## Первый запуск

```
python -m filepost.cli --config config.toml init
```

Команда создаёт `config.toml` (если его нет), базу и **код регистрации первой станции**.
Код показывается один раз, действует 24 часа, станция по нему получает права
администратора. Дальше:

```
python -m filepost.cli --config config.toml serve
```

## Утилиты администратора

```
station list                 все станции, статус, версия клиента
station enroll [--admin]     выдать код регистрации новой станции
station reset <имя>          отозвать ключ, выдать новый код
station admin <имя>          выдать или снять права администратора
storage report               занято, свободно, ничейные, потерянные
storage verify               сверка БД и диска
db backup <путь>             корректный бэкап живой базы
db verify <файл>             проверка резервной копии
housekeeping [--backup]      разовый прогон уборки
```

`storage verify` **обязателен** после восстановления БД из копии: база и хранилище
после этого заведомо расходятся в обе стороны.

## Структура

| Модуль | Назначение |
|---|---|
| `config.py` | Загрузка `config.toml`, значения по умолчанию из 2.6 |
| `db.py` | Схема из 2.3, WAL, соединение на поток, корректный бэкап |
| `auth.py` | Коды регистрации, ключи станций, токены с TTL |
| `storage.py` | Резервирование места, чанки, сборка, sha256, `Range` |
| `messages.py` | Сообщения, вложения, статусы доставки, поиск ничейных |
| `journal.py` | События для синхронизации и аудит-журнал |
| `recovery.py` | Процедура старта из 2.12 и сверка хранилища |
| `housekeeper.py` | Уборка `tmp\`, обрезка событий, ночной бэкап, очистка по сроку |
| `discovery.py` | UDP-ответчик автопоиска (по умолчанию выключен) |
| `app.py` | FastAPI: endpoint'ы из 2.4 |
| `cli.py` | `init`, `serve`, `station`, `storage`, `db`, `housekeeping` |

## Установка службы

```
install-service.cmd
```

Ставит службу через NSSM (положите `nssm.exe` рядом), настраивает автозапуск,
перезапуск при падении, ротацию журналов и правило брандмауэра с `profile=any`.

## Что настроено под гигабайтные передачи

Умолчания Uvicorn рассчитаны на API с JSON, поэтому в `serve` заданы явно:
keep-alive 120 с (между чанками бывают паузы, и рвать соединение каждые 5 секунд
означает переустанавливать его сотни раз за файл), graceful shutdown 30 с (служба
не должна висеть вечно, если кто-то качает пятигигабайтный файл), отключён
перезапуск воркера по числу запросов — он оборвал бы активные передачи.

## Исключение антивируса

Realtime-сканирование режет скорость записи в разы и может перехватить файл ровно
в момент сборки из чанков. `install-service.cmd` заводит исключение сам, но проверить
результат нужно руками — политики домена могут его отменить.

**Microsoft Defender**, PowerShell от администратора:

```powershell
Add-MpPreference -ExclusionPath    "D:\FilePost"
Add-MpPreference -ExclusionProcess "D:\FilePost\.venv\Scripts\python.exe"
```

Проверка, что применилось:

```powershell
Get-MpPreference | Select-Object -ExpandProperty ExclusionPath
Get-MpPreference | Select-Object -ExpandProperty ExclusionProcess
```

Снять, если понадобится: те же команды с `Remove-MpPreference`.

Исключаются оба: каталог и процесс. Только каталога мало — Defender проверяет ещё
и сам исполняемый файл службы; только процесса мало — файлы пишутся на диск и
сканируются при записи.

**Сторонний антивирус** (Kaspersky, Dr.Web, ESET). Если он установлен, Defender
обычно отключён и команды выше ничего не сделают — скрипт это скажет. Исключение
заводится в консоли самого антивируса, и нужны два: каталог `D:\FilePost\` и процесс
службы. В корпоративных сборках это часто закрыто политикой и делается через
администратора антивируса, а не локально.

**В домене** исключения могут задаваться групповой политикой, и локальные тогда
игнорируются. Проверяется тем же `Get-MpPreference` — если после `Add-MpPreference`
пути в списке не появилось, значит их переопределяет GPO.

### Про безопасность этого решения

Исключение означает, что файлы, лежащие в хранилище, на сервере не проверяются.
Разумно это по двум причинам: сервер их **никогда не выполняет** — только принимает,
собирает и отдаёт байты, а имена на диске вообще UUID; и станция-получатель сохраняет
файл в `downloads\`, где его проверяет уже свой антивирус.

То есть проверка не пропадает, а переезжает туда, где файл действительно открывают.
Если политика требует сканировать и на сервере, правильный путь — не realtime, а
проверка по расписанию в нерабочее время: она не мешает передаче.

## Что осталось до боевого запуска

- Зеркальный том под `storage\`: файлы не бэкапятся осознанно, от смерти диска
  защищает только зеркало (2.13).
- `[backup] path` должен указывать на **другой физический диск**. Если каталог
  недоступен — диск отключили, размонтировали сетевой — уборка не падает, но
  пишет `db.backup_failed` в аудит и показывает ошибку администратору
  в разделе «Хранилище». Молча не работающий бэкап хуже, чем его отсутствие.
- `nssm.exe` рядом с `install-service.cmd`.

## Замечания по переносу на Windows

- Пути в `config.toml` пишутся с двойными обратными слэшами.
- `storage` и `tmp` **обязаны быть на одном томе**: финальное перемещение делается
  через `os.replace`, и между томами это будет копирование гигабайтов, а не мгновенный
  `rename`.
- `storage_path` в БД хранится с обратными слэшами, при чтении нормализуется —
  база, снятая на Windows, читается и на Linux.
